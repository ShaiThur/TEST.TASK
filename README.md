# TN VED regulation ranking

## Описание

Данный проект реализует сопоставление таможенных деклараций и регуляции в порядке убывания релевантности.

## Установка

```
pip install -r requirements.txt
```

Модель `intfloat/multilingual-e5-base` и `BAAI/bge-reranker-v2-m3` должны
быть заранее закэшированы локально (HF_HUB_OFFLINE=1 выставляется пакетом
автоматически) — загрузка не входит в лимит запуска.

## Запуск

```
python run.py --data ./data --out ./out
```

## Тесты

```
pytest tests/
```

### Альтернативы

1. Лексический поиск без использования моделей глубокого обучения
   Принцип: построить BM25-индекс по объединённому тексту регуляций, далее - ранжирование по декларации для топ 10 документов.

Плюсы:

- Простота и скорость реализации
- Детерминированный результат при запусках
- Не требует большого количества ресурсов
- Легко объяснить, почему документ попал в топ (за счет совпадения лексем)
- Хорошо работает на точных терминах, кодах, числах и единицах измерения
- Не требует скачивания и хранения весов моделей

Минусы:

- Подход не улавливает синонимию и переформулировки
- Чувствителен к словоформам без лемматизации
- Не учитывает контекст и порядок слов, работает по принципу BoW
- При коротком или неполном описании декларации пересечение термов с регуляцией может быть слишком слабым, чтобы выделить релевантный документ

2. Поиск на основе эмбеддинговой модели
   Принцип: с помощью эмбеддинговой модели необходимо построить векторные представления текстов, далее, рассчитать косинусное сходство между эмбеддингом декларации и эмбеддингом регуляции и выбрать топ 10 эмбеддингов для каждой декларации.

Плюсы:

- Улавливание смысловой близости и синонимов
- Устойчив к перефразированию и различным формулировкам одного и того же товара

Минусы:

- Плохо работает на редких точных терминах, кодах, числах, единицах измерения
- Зависит от построения корректных чанков для сравнения
- Качество сильно зависит от того, насколько часто домен встречался при обучении модели
- Результат менее интерпретируем — сложнее объяснить, почему выбран конкретный документ, чем при лексическом поиске

3. Гибридный подход на основе прошлых двух
   Принцип: Построить BM-25 индексы, эмбеддинговые вектора, для каждого метода найти топ K > 10, с помощью RRF выбрать топ 10 наиболее подходящих кандидатов.

Плюсы:

- Плюсы от прошлых методов
- Лучше recall, чем любой из прошлых методов по отдельности
- RRF работает по рангам, а не по абсолютным значениям скоров — не нужно калибровать/нормализовать разные шкалы BM25 и косинусного сходства между собой

Минусы:

- Сумма разнородных скор без явной модели релевантности пары
- RRF учитывает только позицию в списке каждого метода, а не "силу" совпадения, поэтому может недооценивать сильного кандидата, если он не попал в топ хотя бы одного из методов
- Появляются дополнительные гиперпараметры для подбора

4. LLM как основной ранкер
   Принцип: подать декларацию и кандидатов из ретирв в промпт LLM и получить от неё ранжированный топ-10 с оценкой релевантности.

Плюсы:

- Потенциально лучше улавливает содержательные правила классификации
- Может рассуждать, а не просто мерить схожесть
- Может использовать примечания и исключения для содержательного сопоставления, а не просто совпадения терминов
- Может дать текстовое объяснение выбора

Минусы:

- Недетерминированность ответа
- Опасность выйти за ограниченное время
- Зависимость от качества промпта
- LLM ранжирует по смыслу, но плохо оценивает степень релевантности числом
- Чувствительность к порядку кандидатов в промпте
- Ограничение контекстного окна не позволяет подать все 360 регуляций сразу
- Ограничение модели до 8B параметров снижает качество "рассуждения" по сравнению с более крупными LLM

## Принятый подход

**Лексический и семантический поиск по векторам + реранкер**
Принцип: построить BM25-индекс и эмбеддинговые вектора, для каждого метода найти топ K > 10, с помощью объединения выбрать пул кандидатов, затем передать его в кросс-энкодер для финального ранжирования топ-10.

Задачи, решаемые поиском и реракером:

- максимизировать recall — не пропустить релевантную регуляцию в кандидаты
- максимизировать precision на верхних позициях, то есть правильно расставить кандидатов по релевантности

Двухэтапная схема retrieval (BM25 + dense, объединённые через RRF) → reranking (кросс-энкодер) берёт сильные стороны трёх подходов и последовательно закрывает их главные минусы:

- recall защищён объединением двух взаимно дополняющих источников (закрывает минусы вариантов 1 и 2);
- точность верхних позиций обеспечена кросс-энкодером вместо эвристической суммы скоров (закрывает минус варианта 3);
- результат остаётся полностью детерминированным и доступным по вычислениям.

## Структура проекта

- `run.py` — точка входа (`python run.py --data ./data --out ./out`)
- `tnved_ranker/` — пакет с логикой, по одному модулю на компонент
  `knowledge`, `text_processing`, `bm25_retriever`, `dense_retriever`,
  `reranker`, `candidates`, `validation`, `pipeline`, `config`, `schema`
- `tests/` — юнит-тесты для парсинга справочника, нормализации текста, объединения кандидатов, валидации формата

### Сомнительные примеры

- D0001, R0020, rank 4

Регуляция описывает мясо мороженой рыбы, в то время как декларация относится к мясу млекопитающего. Высокий ранг при таком категориальном несоответствии указывает на недостатки алгоритма сопоставления в обработке смежных тем.

- D0002, R0025, rank 1

Жидкий концентрат для производства газированного напитка с ароматом колы никак не связан с молочными продуктами. Напиток-кола не имеет отношения к молочной продукции. То, что регуляция заняла 1е место является ошибкой.

- D0003, R0121, rank 1

Декларация — это \*\*витамин С в таблетках, а регуляция R0121 — гормональные контрацептивы . Это абсолютно разные фармакологические группы и назначения. Получение максимального балла для такой пары нелогично.

- D0005, R0076, rank 4

Произошло прямое сопоставление свежих фруктов с соковой смесью на 4-м месте с оценкой 0.21. Это смешение разных уровней обработки товара, что снижает практическую ценность рекомендации.

- D0093, R0066, rank 7

Из общего у регуляции и декларации только наличие сахара, но это разные категории (напиток и овощная консервация). Наличие такой пары в топ-10 показывает, что алгоритм иногда путает продукты с сахаром независимо от варианта их создания.

#### Причины и варианты решения проблемы сопоставления:

Для алгоритма BM-25 возникает проблема в том, что описания содержат часто встречающиеся термины (_«мороженое»_ , _«мясо»_ , _«препараты»_ , _«сок»_ , _«сахар»_ ) . BM25 даёт высокий вес таким словам, если они редки в корпусе, но в данном случае они широко распространены, что приводит к ранжированию нерелевантных регуляций, содержащих те же ключевые слова (например, _«мясо рыбы мороженое»_ для свинины).

Ээмбеддинги хорошо улавливают общие темы, но плохо различают узкие подкатегории. Так, «мясо» и «рыба» лежат близко в векторном пространстве как «продукты животного происхождения», а «соки» и «фрукты» – как «растительная продукция».
